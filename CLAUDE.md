# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Current state

This repository holds two take-home challenge briefs and a SWE lamp playground in `SWE_route/simulation/`. Current implementation work targets SWE simulation. From that directory, run `uv sync --locked`, `uv run --locked python -m lamp_sim`, and `uv run --locked pytest -q` with Python 3.12. MuJoCo physics is the default; the viser browser retains original kinematic playback as a comparison mode. The library contains 126 JSON gestures: nine original clips and 117 entries from all three rings of the supplied emotion wheel, grouped into six family selectors. See `SWE_route/simulation/gestures/emotions.md` for the complete catalog. A headless benchmark logs requested/actual motion, timing, memory, and contacts; the preserved October 1 baseline covers only the original nine clips. See `SWE_route/simulation/benchmarks/README.md` for evidence and assumptions. No formatter or linter is configured. See the simulation README for controls, limitations, and Ubuntu instructions. `parameter_golf/` is reference code copied unchanged from the user's earlier `DL-Team-Proposal` repo (small-language-model trainers, data download scripts, and plotting tools). It is not part of either challenge, and several of its trainers import the Unix-only `fcntl` module, so they do not run natively on Windows.

## The two routes

`ML_route/README.md` is a real-time multimodal emotion challenge built on the MELD dataset. The user picks one track, either text plus audio or text plus vision, and on 2026-10-15 the user chose text plus vision. On 2026-10-16 the user changed the submission to the text plus audio track, because the working head reads Whisper's words and HuBERT's voice features; the vision benchmark stays as evidence of what was tried. The ML route is the official submission, the repository is public, the root `README.md` is the submission README, the trained head is committed at `ML_route/heads/meld-head.json`, and the large files (features and Whisper transcripts) go in a GitHub Release. The prototype produces a MELD emotion category plus short grounded response text from input that arrives over time. The whole local inference path may hold at most 6 billion total learned parameters, counting every encoder, backbone, adapter, projector, head, and auxiliary generator. Remote inference does not satisfy the core task. The timebox is two to three days, and the submission must report hardware and observed resource use.

`SWE_route/starter_pack/` is a live character challenge around a simulated five-DOF desk lamp. The laptop camera, microphone, and speaker act as the robot's senses and voice, and the URDF provides the simulated body for motion and light. Cloud APIs are allowed for perception and speech, but the submission must state what data is sent, where decisions are made, and why. The timebox is six to eight hours. The deployment target is a clean Ubuntu 24.04 laptop with four CPU cores, 8 GB of RAM, no discrete GPU, and standard Linux audio. Development may happen on another operating system, but the deployment story must still address that Ubuntu target.

The two routes disagree on remote inference, so check which route applies before proposing a cloud model.

## ML route: compute, data, and models

The ML brief sets no hardware limit. It asks only that the submission report the hardware used and the resources observed. The user's own PC has a GTX 1070 Ti (8 GB, Pascal, no bf16), so on 2026-10-14 the user chose Runpod for all ML work. Training runs on a pod, and the demo also runs entirely on one pod. MELD scenes are fed from disk at real-time speed, so no input or output crosses the network during inference. The pod is the local machine for this project. Every model in the inference path runs on it, and none is called over a network, so the demo is not remote inference. Do not raise the pod as a remote-inference risk. The submission reports the pod's GPU as its hardware. The planned GPU is an A40 with 48 GB. Never create, start, or stop a pod unless the user asks in that conversation. Pod sizing and prices are in `docs/research/runpod-pod-sizing.md`.

MELD is unpacked in `ML_route/data/MELD.Raw/`, which is gitignored. It came from https://web.eecs.umich.edu/~mihalcea/downloads/MELD.Raw.tar.gz. The label files are `train_sent_emo.csv`, `dev_sent_emo.csv`, and `test_sent_emo.csv`. The clips are `train_splits/` (9,989 mp4 files), `dev_splits_complete/` (1,112), and `output_repeated_splits_test/` (2,747). The test folder also holds 2,060 macOS `._*` stub files, which a loader must skip. MELD has no separate audio files. The sound is an AAC audio stream inside each mp4. Of three clips checked on 2026-10-14, all were 48 kHz, two were stereo and one was 6-channel. The audio therefore needs extracting with ffmpeg and downmixing to mono.

There are three versions of the label CSVs, kept on purpose so the effect of changing the text can be measured. `ML_route/data/MELD.Raw/` holds MELD exactly as published. `ML_route/data/MELD.Completed/` holds fixed copies of the three CSVs only, and the clips stay in `MELD.Raw`. Running `ML_route/text_fixes/apply_fixes.py` rebuilds `MELD.Completed` from `MELD.Raw` and never writes to `MELD.Raw`. It maps MELD's broken Windows-1252 characters to real punctuation and collapses repeated spaces in all three splits. In train and dev only, it then applies the reviewed word fixes in `ML_route/text_fixes/fixes.csv` and the 340 reviewed audio fixes in `ML_route/text_fixes/audio_fixes.csv`. The word fixes cover clear written mistakes, such as you're for your, misspellings, and `?` in place of an apostrophe, while spoken style such as "gonna" and stutters stays as it is. The audio fixes finish cut-off lines and restore skipped words from the audio. The test split keeps its published words, so test scores stay comparable with other MELD results. On 2026-10-15 the user dropped `MELD.Clean`, the earlier version with only the character and word fixes, so the word fixes and audio fixes are no longer measured separately. The Rust code in `hello_world` reads `MELD.Completed`. `ML_route/data/MELD.Whisper/` holds a Whisper large-v3-turbo transcript of every clip in all three splits, as JSONL with segment confidence and word times, and as a copy of each label CSV with Whisper's text as the utterance. `ML_route/text_fixes/transcribe.py` builds it on the local GPU from that folder's `.venv`, and a rerun skips clips already done. `docs/research/meld-data-quality.md` records the data problems found, including overlapping clips, missing lines, cut-off transcripts, wrong speaker names, and 6-channel audio, how the transcripts and fixes were made, and the planned experiment that compares the three versions.

MELD labels each line with one of seven emotions: neutral, joy, surprise, anger, sadness, disgust, and fear. The user's reference emotion wheel is `docs/images/emotion-wheel.png`. Its seven core emotions are Happy, Sad, Angry, Fearful, Surprised, Disgusted, and Bad. The first six map to MELD's joy, sadness, anger, fear, surprise, and disgust. The wheel's Bad and MELD's neutral have no match. This wheel differs from the one transcribed in `SWE_route/simulation/gestures/emotions.md`, which has six core emotions and different outer rings.

The candidate models live in `docs/research/ml-model-catalog.json`, which also feeds the explainer page `docs/explainers/meld-head-training.html`. On 2026-10-14 the user removed every model that a newer successor has replaced, usually a newer version from the same maker. CLIP counts as replaced by SigLIP 2. The catalog's `removed` list names each one and its replacement, so do not suggest those models again. On 2026-10-15 the user also dropped the voice detector step, because each MELD clip holds one spoken line, so Silero VAD, TEN VAD and Pipecat Smart Turn left the catalog and the page; they are not in `removed`, since nothing replaced them. On 2026-10-16 the user eliminated the speech-to-text and text-encoder candidates they did not choose, keeping them only for notes and reports: the catalog's `not_chosen` list holds the 9 speech-to-text models and 12 text encoders with their full entries, leaving 59 candidates, and the explainer library, `asr_race.py`, `run_all.sh`, `features.py` and `heads.py` now name only Whisper large-v3-turbo int8, EmbeddingGemma 300M and the EmoBERTa-large backup. `nemotron_text.py` was deleted. The A40 results in `ML_route/bench/results/` keep every measured model. For voice the user settled on HuBERT-large, with emotion2vec+ large as the backup ("let's stick with HuBERT-large and emotion2vec+ large as backup"). Paired with EmbeddingGemma, HuBERT-large scored 61.6 and emotion2vec+ large 57.7, although emotion2vec+ was the best voice encoder alone (47.9). emotion2vec+ needs the FunASR package, which the player venv lacks. The other 8 voice encoders moved to the catalog's `not_chosen` list, leaving 51 candidates, and `features.py` lists only these two. `docs/research/vlm-emotion-models.md` surveys open vision-language models that read emotion on people, from a verified multi-agent search on 2026-10-15; it did not change the catalog.

The user wants to train in Rust, which is their learning track. `ML_route/hello_world/` is the user's first Cargo crate. Run `cargo run` from that folder. It prints a greeting, then writes five training dialogues as tables to `dialogues.txt`, read with the `csv` crate. `cargo run --bin demo -- <Dialogue_ID>` runs `src/bin/demo.rs`, which plays a test dialogue's clips in order with ffplay (test dialogue 149 when none is given, `--no-play` to skip playback). After each clip it asks `serve.py` for Whisper's words, the head's emotion and LFM2.5's reply, and prints them with each step's time. When a server is not answering, it falls back to a random emotion marked `(random)` and a canned reply from `REPLIES` marked `(placeholder)`; `--server <url>` points it at another address. `ML_route/player/build_player.py` writes the same demo as a browser page, `ML_route/data/meld-player.html`, from the template `player.html`. It sits beside `MELD.Raw` so its relative clip paths resolve. The page also inlines the SWE route's desk lamp under the video. `build_player.py` embeds the URDF, `SWE_route/simulation/models/derived/scene.json`, the shade mesh, the gesture library in `SWE_route/simulation/gestures/*.json`, and the script that `npm --prefix SWE_route/simulation/viewer run build:embed` writes to `viewer/embed-dist/lamp-embed.js`. It refuses to build when that script is missing or was built from sources that have changed since. A gesture edit therefore needs only a page rebuild, while a change under `viewer/src/` needs the script rebuilt first. The lamp is a TypeScript port of the direct playback in `lamp_sim/motion.py`, not the MuJoCo simulator, because the Rust server's socket rejects the page's origin. When a line gets its emotion, from the head or its random fallback, the lamp plays a clip picked at random within that emotion's family on the emotion wheel, never repeating the family's previous pick. Joy plays a Happy clip, sadness a Sad clip, anger an Angry clip, fear a Fearful clip, surprise a Surprised clip, and disgust a Disgusted clip, and each family's pool holds its core clip and every sub-emotion clip. Neutral plays a calm clip picked at random from `idle_hold`, `nod`, `curious` and `scan`. Each output record gets one new field, `lamp_clip`, which holds the played gesture's name. The Lamp box is on by default and off when the system asks for reduced motion. `ML_route/text_fixes/.venv/Scripts/python.exe ML_route/player/serve.py` serves the page at `http://127.0.0.1:8765/meld-player.html` and transcribes each clip live with Whisper on the local GPU when it ends, so the page can show the real transcription time; under any other server the live transcript is simply off. `ML_route/player/.venv/Scripts/python.exe ML_route/player/serve_reply.py` adds the LFM2.5-1.2B-Instruct reply writer in fp16 on port 8768. That venv holds PyTorch 2.14 from the cu126 index, the newest build that still runs on the Pascal 1070 Ti. `serve.py` forwards `/api/reply` to it, and forwards `/api/emotion` and `/api/predictions` to `serve_emotion.py` on port 8769; `/api/predictions?split=` returns the head's emotion for every clip of a split from the saved features, which the Score tab uses for its "Emotion head, all of test" row and makes Whisper and LFM2.5 take turns on the GPU, and the page shows one reply per line. On 2026-10-16 the user decided that the player is judged and shown on MELD's test split only, because the emotion head trained on the train lines, so live emotions on train dialogues would look too good. By default, at the user's choice, the reply also sees the dialogue's earlier lines as a plain transcript, without the model's own earlier replies, and a menu beside Live reply switches it to the line alone. Until a real classifier exists, both replies answer MELD's own emotion label rather than the random guess. The system prompt asks for one sitcom-friend sentence with two example replies and, at the user's request, no opening "Hey" plus the person's name, because naming someone in a one-on-one conversation sounds slightly serious or hostile; `reply_length` asks for about as many words as the line has (2 to 20) and gives about one line in four, picked by a checksum of its text, a long turn of up to 20 words, and `clean_reply` strips example layout the model copies. `ML_route/bench/` holds the overnight benchmark scripts that run on the Runpod pod, and `ML_route/bench/results/` holds their results. ## SWE route: which documents are authoritative

`CHALLENGE.md` and `SUBMISSION.md` are the current specification. `README.md` in the same folder is a stale earlier draft. It refers to a six-DOF URDF and a Google Drive link, and it lists only four demonstration moments. `CHALLENGE.md` adds a fifth moment, goal-directed action, in which a spoken goal about the live scene drives a sequence of lamp actions and the scene is observed again before the goal is complete. The shipped URDF is five-DOF, which confirms that `CHALLENGE.md` is current.

`SUBMISSION.md` defines the deliverables and the scoring rubric. The deliverables are source code with dependency declarations, Ubuntu setup and run instructions, and a technical note of at most two pages. The note must contain one architecture and data-flow diagram, must cover protocol, model-to-action, simulation, deployment, and key design choices, and must report engagement reliability, response latency, and CPU and memory measurements. The rubric weights architecture and protocol at 25%, character integration at 20%, perception, action, and memory at 20%, deployment at 15%, physical reasoning at 10%, and evidence and communication at 10%.

## SWE route: URDF facts that take a careful read

The file is `SWE_route/starter_pack/robot/dummy_lamp_5dof.urdf`. The actuated chain from base to head is `base_yaw_joint` (z axis), `shoulder_pitch_joint` (y), `elbow_pitch_joint` (y), `neck_yaw_joint` (z), and `head_pitch_joint` (y). Each joint has a hard `<limit>` and a tighter `<safety_controller>` soft range. Control code should clamp to the soft range.

The URDF deliberately contains no fixed world joint, no simulator plugins, no transmissions, and no controllers. Whatever simulator or visualizer is chosen must anchor `base_link` itself. The mesh path `assets/lamp_shade.stl` is relative to the URDF's own directory, so loaders must resolve it from there.

The origin of `head_pitch_joint` carries a 180° yaw. At zero configuration, the lamp head therefore faces the base frame's −x direction, opposite to the direction in which positive shoulder and elbow pitch lean the arm. Positive head pitch tilts the shade downward. Anyone computing where the lamp is looking, or mapping a target in the scene to joint angles, needs to account for this flip.

`light_emitter_link`, `camera_link`, and `speaker_link` are semantic frames with no behavior attached. The software adapter decides what they do. `camera_link` rides on the lamp head, but the challenge says the laptop camera does the seeing, so moving the simulated head does not move the real camera view. That mismatch shapes how the "observe the scene again" step can work, and it is the kind of physical-reasoning point the rubric scores.

## Repository hygiene

`SWE_route/__MACOSX/` and the `.DS_Store` files are macOS zip-extraction artifacts, not challenge content. The root `.gitignore` excludes them, along with Python caches, `.env` files, downloaded datasets, and `*.pt` weights, so a trained head that belongs in the submission needs `git add -f`. `.gitattributes` sets `* text=auto`, so line endings are normalized to LF on commit.
